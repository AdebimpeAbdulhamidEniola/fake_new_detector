Lesson 1 · Security

Deleting a stranger's transactions

You will log in as Bob and destroy Alice's financial records — using nothing but a valid Bob token. Then you'll make that attack impossible.

Severity: High OWASP API1:2023 — BOLA

Every endpoint that takes an ID from the client and acts on that object must check that the logged-in user is allowed to touch that object. Your transaction endpoints don't. They trust the ID and nothing else. This single class of bug — Broken Object Level Authorization — is the #1 risk on the OWASP API Security Top 10, and it's the first thing a sharp interviewer will try against a CRUD API.

The claim we're about to prove

Any authenticated user can read the ID of another user's transaction and then update or delete it, because the code looks the row up by id alone and never compares it to req.userId.

Where the hole is

Open src/models/transaction.model.ts. The delete is literally:

export const deleteTransaction = async (id: string) => {
    return await prisma.transaction.delete({
        where: { id }            // ← only the id. whose transaction? nobody asks.
    })
}

And the controller in src/controllers/transaction.controller.ts checks that you are logged in, then throws the user ID away:

const userId = req.userId;
if (!userId) throw new AppError("User not authenticated", 401);
// userId is never passed down — ownership is never checked
const transaction = await deleteTransaction(req.params.id);

Being logged in is authentication. Being allowed to touch this specific row is authorization. The guide says it plainly: "a user may be authenticated successfully… but still not be authorized to access a specific resource" (Backend-Engineers-Guide/notes/08_security/01_auth.md). Your code does the first and skips the second.

Break it — in Postman

Run your API locally first (npm run dev), with your database connected. Set a Postman variable baseUrl = http://localhost:4100 (or whatever your PORT is).

  1. Create Alice. POST {{baseUrl}}/api/auth/signup, body (JSON): 
    { "email": "alice@test.com", "password": "password123",
  "confirmPassword": "password123", "name": "Alice" }
  2. Create Bob. Same request, bob@test.com / "name": "Bob".
  3. Mark both verified. Login refuses unverified emails, and SendGrid won't deliver locally, so flip the flag straight in the database. In a terminal: 
    psql "$DATABASE_URL" -c 'UPDATE "User" SET "isVerified" = true;'
    (One-time shortcut for local testing only — never do this in production.)
  4. Log in as Alice. POST {{baseUrl}}/api/auth/login with Alice's email + password. Copy data.token from the response → call it TOKEN_A.
  5. Log in as Bob. Same, → TOKEN_B.
  6. Alice records a transaction. POST {{baseUrl}}/api/transactions, Header Authorization: Bearer TOKEN_A, body: 
    { "amount": 5000, "category": "Salary", "type": "INCOME" }
    Copy the returned data.id → TX_ID. This row belongs to Alice.
  7. 🔴 The attack. Now be Bob. DELETE {{baseUrl}}/api/transactions/TX_ID, Header Authorization: Bearer TOKEN_B. No body.
    You get 200 "Transaction deleted successfully". Bob just deleted Alice's data with his own token. Try the update variant too: PUT {{baseUrl}}/api/transactions/TX_ID with { "amount": 1 } and Bob's token — Bob can rewrite Alice's money.
  8. Confirm the damage. As Alice (GET {{baseUrl}}/api/transactions, TOKEN_A) — her transaction is gone. She never consented, never saw it.

That is the whole vulnerability. No special tools, no SQL injection — just an ID Bob wasn't supposed to be able to use. In the real OWASP scenarios this is how attackers pull "the sales data of thousands of e-commerce stores" or unlock cars that aren't theirs.

Fix it — scope every object to its owner

The rule (OWASP "How To Prevent"): in every function that uses a client-supplied input to reach a record, check that the logged-in user is allowed to perform the action on that record. We push the user's ID into the query so the database can only ever touch rows that belong to them.

1. Make the model owner-aware

src/models/transaction.model.ts — require userId and filter on it. updateMany/deleteMany let us match on both id and userId and tell us how many rows matched:

export const updateTransaction = async (
  id: string, userId: string, data: Partial<TransactionInput>
) => {
  const result = await prisma.transaction.updateMany({
    where: { id, userId },   // ← must match the owner too
    data,
  });
  return result.count; // 0 = not yours (or not found)
};

export const deleteTransaction = async (id: string, userId: string) => {
  const result = await prisma.transaction.deleteMany({
    where: { id, userId },
  });
  return result.count;
};

2. Make the controller enforce it

src/controllers/transaction.controller.ts — pass the ID down, and turn "0 rows touched" into a clean error instead of a silent success:

const count = await deleteTransaction(req.params.id, userId);
if (count === 0) {
  throw new AppError("Transaction not found", 404);
}
handleResponse(res, 200, "Transaction deleted successfully");

Do the same in updateTransacctionController. We return 404, not 403, on purpose: telling Bob "403 Forbidden" would confirm the row exists. 404 leaks nothing about other users' data.

Re-test in Postman — same requests, new outcome

Repeat step 7 (Bob's DELETE on Alice's TX_ID): now 404 "Transaction not found". Bob is blocked. Then delete it as Alice (TOKEN_A): 200. Owners can act; strangers can't. The hole is closed.

Lock it so it can't come back

A fix with no test rots. The OWASP checklist's last line is "Write tests to evaluate the vulnerability… Do not deploy changes that make the tests fail." Your regression test, in words, is:

// Bob must NOT be able to delete Alice's transaction
// 1. create alice + bob, create a tx as alice
// 2. DELETE /api/transactions/:aliceTxId  with bob's token
// expect(status).toBe(404)
// expect(aliceTxStillExists).toBe(true)

We'll turn this into a real, runnable test in the testing lesson — and that same test is what a CI pipeline will run on every push. For now, the words are enough: you know exactly what "fixed" means.
